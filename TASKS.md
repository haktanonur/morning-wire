- [x] TASK-004: `src/app/fetchers/sports.py` — fetch results from API-Football (4 leagues), balldontlie.io (NBA), Ergast (F1).

The category is football only.
- [x] TASK-005: `src/app/summarizer.py` — call the Claude API with a category-specific prompt to turn raw fetcher output into a short summary.
  - Acceptance: one prompt template per category; the Anthropic API call is mocked in tests; output length stays within a sane bound (see `PLAN.md` §5).
  - Inherited from earlier tasks — the fetchers deliberately do not filter, so the prompts must: (a) Finnhub's `general` category mixes macro/market stories with general world news, so the markets prompt has to ignore the non-market ones; (b) AA Gündem carries sports stories, so the news prompt must not restate what the sports category already covers; (c) `Article.region` is `TR` or `WORLD`, so the news prompt can cover both halves without blending them.
  - Notes: unlike the fetchers, these functions **do** raise (`SummarizationError`) — a fetcher returning nothing is a normal outcome the summary can describe, but a failed API call leaves nothing to print, so TASK-006 needs an exception to turn into `[unavailable: ...]`. Only the exception *type* goes into the message, so a provider error can never carry the API key into a log. Empty input short-circuits to `NO_DATA` (or `NOTHING_NOTABLE` for sports) without spending an API call. Length is capped at `MAX_SUMMARY_CHARS = 600` now rather than after Phase 2, since SMS segments are the real constraint; `_trim` cuts on `". "` rather than `"."` because a decimal point in a price was being read as a sentence end. Three prompt fixes came out of live runs, not tests: the model announced *absent* data ("No Formula 1 results were provided"), leaked AA's sports stories into the news section, and dropped the world half entirely because the feed is 16 TR vs 8 WORLD — the news prompt now demands exactly two sentences per region.
- [x] TASK-006: `src/app/main.py` — CLI entrypoint. Calls all 4 fetchers, summarizes each, prints the result to the terminal grouped by category (see `PLAN.md` §6 for the output format). Each category wrapped in try/except so one failure doesn't stop the others.
  - Acceptance: running `python -m app.main` with all external calls mocked produces a full 4-section printed report in a test.
  - Notes: `build_section()` is the single error-isolation boundary — nothing a fetcher or the summarizer raises gets past it. The `[unavailable: ...]` reason is `str(exc)` falling back to the exception type, which is why `summarizer.py` sanitizes its own message rather than leaving that to `main.py`. The report goes to stdout and warnings to stderr, so the output stays pipeable. A `runpy.run_module` test for the literal `python -m` path was written and then **removed**: `run_module` re-executes the module, so the mocks bound to the already-imported `app.main` don't apply and the test silently hit the real network (4.2s of the suite's runtime). `main()` is what the `__main__` guard calls, so testing `main()` directly covers the same path honestly. The end-to-end run also caught a summarizer regression: naming Formula 1 in `SPORTS_PROMPT` made the model report its *absence* on race-free weeks, so the prompt now names no sport at all and just follows the data.

## Phase 2 — SMS Delivery (MacroDroid webhook → owner's phone)
- [x] TASK-016: Turkish brief output + `src/app/sms_text.py` — make the summaries Turkish and fold them into GSM-7 so an SMS segment holds 153 characters instead of 67. Prerequisite for TASK-007, which is why it lands first.
  - Acceptance: `to_gsm7` output contains nothing outside the GSM-7 alphabet; the terminal output keeps proper Turkish.
  - Notes: **the "160 chars per SMS" assumption in `PLAN.md` §5 was wrong for this project** — Turkish forces UCS-2 (67 chars/segment), so the untouched brief cost 28 segments/day. Folding the diacritics plus dropping `MAX_SUMMARY_CHARS` from 600 to 400 brings that to ~11; the fold contributes more of the saving than the shorter cap. See `docs/adr/0005`. The fold uses NFD decomposition rather than a hand-written table, which covers `ç ğ ö ş ü` and the accented Latin letters for free; only dotless `ı` and typographic punctuation (em dash, curly quotes, ellipsis) need explicit entries — and those matter, since one em dash left in place drags the whole message back to UCS-2. A live-run bug cost six debugging runs and is worth remembering: the news summary kept losing its world half, which looked exactly like the model ignoring the prompt, but the model *was* writing it — the reply ran to 486 characters and `_trim` cut at the last sentence boundary under the cap, amputating it. `_trim` now logs a warning when it fires, and the news prompt carries a per-sentence budget so it stops overrunning. Prompts stay English and ask for Turkish output.
- [x] TASK-007: `src/app/sender.py` — send a category-tagged SMS. Must pass the body through `sms_text.to_gsm7()`.
  - Acceptance: a send failure for one category doesn't block the others; the outbound call is mocked in tests.
  - Notes: **Twilio was dropped before any of it was committed** — its Turkey guidelines prohibit P2P traffic (exactly this use case) and demand a registered alphanumeric sender id with corporate documents; NetGSM has the same registration problem. Replaced by a **MacroDroid webhook**: one HTTP GET per category to the owner's phone, which sends the SMS from its own SIM. That removed the `twilio` dependency again (`requests` covers it) and replaced `load_twilio_settings()` with `load_macrodroid_settings()` — the trigger URL *is* the credential, so it lives in `.env`, and only the exception type is ever logged because `requests` quotes the failing URL in its message. **Three things about MacroDroid are not visible from this repo and are easy to get wrong** (verified against the MacroDroid wiki, not assumed): a query parameter only populates a variable that *already exists* on the phone, matched by exact case — a name mismatch sends an empty body and still returns 200; the macro must reference it as `{v=message}`, not `{message}`; and the recipient number stays in the macro, which also keeps a real phone number out of the repo. The URL is built by hand rather than with `requests`' `params=`, which encodes a space as `+` where MacroDroid documents `%20` and says nothing about `+`. Biggest consequence: **`200 ok` only means the relay queued a push** — a phone that is off, offline or out of credit answers identically — so the result type reports `accepted`, deliberately not `delivered`, and TASK-013's failure logging cannot cover the last hop. See `docs/adr/0006`.
- [x] TASK-017: Raise `MAX_SUMMARY_CHARS` from 400 to 590 so `_trim` stops amputating sentences.
  - Acceptance: the cap plus the longest category tag still fits 4 GSM-7 segments, asserted rather than commented.
  - Notes: found by the TASK-007 live run — 3 of the 4 categories were trimmed (572, 490 and 430 characters) and markets lost its whole closing sentence. **The cap value was only half the bug.** The other half was that 400 was simultaneously the hard cap *and* the number `SYSTEM_PROMPT` asks the model for, so there was zero headroom and any overshoot cost a sentence. They are now separate numbers doing separate jobs: the prompt still asks for 400, the cap allows 590, and the ~1.5× margin covers the ~1.4× overshoot measured live. **The prompts were deliberately not changed** — raising the stated target would just move the overshoot up with it. Raising the cap is only affordable because the SMS now leave the owner's own phone (`docs/adr/0006`); under Twilio the 3-segment budget was a real bill. `CONCATENATED_SEGMENT_UNITS` moved into `sms_text.py` and a test now checks the arithmetic, because ADR 0005 got it wrong once by counting `[` and `]` as one unit each when they are escape pairs — that error is invisible at runtime, the message just quietly takes an extra segment. It also rules out the 600 originally proposed here: 600 + 14 = 614 > 612.
- [x] TASK-008: Update `main.py` with a `--dry-run` flag — default behavior sends real SMS via `sender.py`; `--dry-run` reuses the Phase 1 terminal-print path instead.
  - Acceptance: `--dry-run` calls nothing in `sender.py` and works with no SMS credentials configured; the default path sends one message per category.
  - Note: `sender.send_report()` takes `(heading, body)` tuples rather than `main.Section`, so `main.py` depends on `sender.py` and not the reverse. Converting is TASK-008's job.
  - Notes: the report is printed in **both** modes and printed *before* sending, so a delivery failure still leaves the briefing readable — sending is an extra step on the Phase 1 path rather than a branch away from it. `main()` now returns an exit code and **`__main__` calls `sys.exit(main())`**: without it a scheduled run whose SMS all failed would still go green, and the relay's failures are otherwise invisible. A category that failed to build is still sent, as `[unavailable: ...]` — the reader is owed the fact that a source died. The delivery summary says "accepted", never "delivered", for the reason in `docs/adr/0006`, and it names the refused categories without their error strings, which is what keeps the trigger URL out of stdout. `--dry-run` deliberately does not touch `load_macrodroid_settings()`, so the Phase 1 path still runs on a machine with no `.env` SMS entry at all; a test asserts that by omitting the send fixture.

## Phase 3 — Scheduled Deployment (GitHub Actions)
**TASK-009 through TASK-012 were deleted, not deferred.** They were the AWS route — a `lambda_handler.py` wrapper, a dependency bundle, an EventBridge rule and a Secrets Manager deploy script — and `docs/adr/0007` replaced all four with a scheduled workflow in a repository that already runs GitHub Actions. `src/app/lambda_handler.py` will not be written: `main.py` is already the entry point, and the wrapper existed only to satisfy Lambda's calling convention. The numbers are left unused rather than recycled so the notes above still refer to something.

- [x] TASK-019: `.github/workflows/daily-brief.yml` — scheduled workflow running `python -m app.main` at `0 3 * * *` (06:00 Istanbul; since TASK-022 the cron is `47 2 * * *`), with the four secrets from GitHub Actions secrets and a `workflow_dispatch` trigger for manual runs.
  - Acceptance: a manual dispatch delivers the four SMS; a failed send turns the run red.
  - Notes: **it needs a fifth secret, `PORTFOLIO_JSON`.** `config/portfolio.json` is gitignored real holdings, so it is not in the runner's checkout and the portfolio category would have been `[unavailable: ...]` every single morning — the one part of this that no test could have caught, since tests mock the fetcher. It is written from the environment rather than interpolated into the shell, so its contents cannot be executed. The `dry_run` dispatch input is compared against the string `"true"`, not tested for emptiness: an unticked checkbox sends the literal `"false"`, which is truthy to `${VAR:+...}` and would have silently suppressed every send. stdout goes to `/dev/null` — the SMS is the output, and the run log would otherwise hold the whole briefing including the portfolio, which is only safe while the repo is private. `pip install -e .` without the dev extras; those belong to `ci.yml`. Cannot be tested from a branch, because scheduled workflows only run on the default branch — manual dispatch after the merge is the only real test.

## Phase 4 — Hardening
- [x] TASK-018: `tests/conftest.py` — autouse guards so no test can read the developer's real credentials or open a real connection.
  - Acceptance: a test that sets no environment variable of its own gets `MissingEnvVarError`, not the real key; an unmocked HTTP call raises instead of going out.
  - Notes: `config.py` calls `load_dotenv()` at import, so every test already had the real `.env` in reach and only convention kept it unused — the failure mode is a test that passes locally against live credentials, spends real quota or fires a real SMS, then fails in CI where no `.env` exists. It had happened once already: the `runpy` test removed in TASK-006 silently hit the real network for 4.2s. The guarded variable list is checked against `config.py`'s own source with `ast` rather than kept in sync by hand, so a newly added secret cannot quietly fall outside the guard. The network block patches `socket.connect`/`create_connection`, which sits below `responses` and `pytest-mock` and so leaves every properly mocked test alone. The whole suite passed unchanged, which says the convention was being followed — the point is that it is no longer a convention.
- [x] TASK-013: Standardize the run log format (which category, how long it took, success/failure) so the workflow log is readable at a glance.
  - Acceptance: every category leaves exactly one line naming itself; the whole log goes through `logging` with one format; third-party loggers stay at WARNING.
  - Notes: was "CloudWatch log format" — the destination is now the GitHub Actions run log (`docs/adr/0007`), but the content question is unchanged. Only stderr survives into that log; TASK-019 discards stdout so the briefing is not written into it. The first live run is what specified this task: its entire output was a trim warning that did not say **which** category had lost a sentence, plus the delivery summary. So the summarizer's warning now names its category, and `build_section` logs name, duration and summary length — length because with stdout discarded there is otherwise no way to tell a summary that nearly overflowed from one that fitted easily. The delivery summary moved from `print` to `logging` so the log has one shape rather than two, and it is logged at ERROR when the relay refused anything. INFO is raised on the `app` logger rather than the root: on the root it would also switch on the Anthropic client's HTTP logger and bury four category lines under one request line per call.
- [x] TASK-014: End-to-end integration test covering the full pipeline — `tests/test_pipeline.py`.
  - Acceptance: only the edges are stubbed (yfinance, Finnhub HTTP, feedparser, football-data HTTP, the Anthropic client, the MacroDroid webhook); everything between them runs for real.
  - Notes: widened past "dry-run", because the send path is where the untested seams are — the `Section`-to-tuple conversion, the category tag, the GSM-7 fold and the send order are all crossed by no unit test. A marker planted in each source's response is echoed back by the stubbed model and then asserted in the outbound query string, so one line covers fetcher → summarizer → `sms_text` → `sender` for a category. The expected strings are written by hand rather than computed, so a fold regression cannot be self-consistent: mutating `build_message` to skip `to_gsm7` turns two of the five tests red, which is what says the assertion is load-bearing. Also covers the cases only an end-to-end test can reach — one dead source costing only its own category, `--dry-run` sending nothing, and a refusing relay returning exit code 1 without losing the terminal report.
- [x] TASK-015: Update README with deployment steps (GitHub Actions secrets + the phone-side macro, not AWS).
  - Acceptance: someone with the repo and a phone can get to a working morning brief from the README alone, without opening an ADR.
  - Notes: the GitHub half already existed; the missing half was the phone, which lived only inside `docs/adr/0006`'s narrative — an ADR records *why* a decision was made and is the wrong place to keep a setup procedure. Written as "Part 1: The Phone" before "Part 2: The Scheduled Run" because the order is load-bearing: the macro is what produces `MACRODROID_TRIGGER_URL`, so nothing else can be configured first. Each step that carries a silent failure says so — the `message` variable must exist *before* the macro or MacroDroid sends an empty body and the relay still answers `ok`; `{v=message}` is a variable reference and `{message}` is sent literally; battery optimisation can swallow the 06:00 push. The manual test tells the reader to watch the phone rather than the HTTP response, because the response is the same either way.
- [ ] TASK-020: Bring the model's reply length back under the cap, or accept a fifth SMS segment.
  - Context: the first live run trimmed a summary at **704 characters** against a prompt asking for "under 400" — a 1.76x overshoot, well past the ~1.4x that TASK-017 sized `MAX_SUMMARY_CHARS = 590` for. `_trim` cut a real sentence out of a delivered SMS.
  - The cap cannot absorb it: 590 plus the 14 GSM-7 units of `[PORTFOLIO] ` is 604 against a 4-segment ceiling of 4 × 153 = 612. So the fix is either prompt-side (a stricter, better-obeyed length instruction, or `max_tokens` used as the real limiter) or a deliberate move to 5 segments — which is now affordable, since ADR 0006 moved sending off metered Twilio and onto the owner's own SIM. The 3-segment budget in ADR 0005 was a cost decision that no longer has a cost behind it.
  - Needs one live measurement per category before choosing: TASK-013's log now records each summary's length, so a few scheduled runs will say how often this actually happens and to which category.
- [x] TASK-021: Fifth category — 15 English vocabulary entries a day from the owner's notebook, sent with the morning brief.
  - Acceptance: `data/vocabulary.txt` parses completely; the same date always selects the same entries; the entries reach the SMS with their Turkish meaning, note and example, and never reach the model.
  - Notes: this is the first category that neither fetches nor summarizes, and both omissions are the point. The entries are already written, in Turkish, by the person about to read them — a summarizer would paraphrase study material into the model's guess at it, so `test_the_vocabulary_is_never_shown_to_the_model` pins the run at exactly four API calls. **Selection is a pure function of the date** (`(toordinal() * 15) % 449`) rather than a stored cursor: the runner is fresh every morning, so a cursor would have to be committed back or cached, and `gcd(15, 449) = 1` means the offset walks all 449 entries before repeating anyway. A re-run after a failed send therefore repeats the morning's list instead of skipping past it. The notebook is **committed, not a secret** — it is data, and the `PORTFOLIO_JSON` lesson from TASK-019 is that a sixth secret is a sixth thing to get silently wrong. One malformed entry is logged and skipped rather than raised, because the file is hand-maintained and growing and one bad edit should not cost the reader the other 448; an *empty* parse does raise, because sending no words is indistinguishable from a quiet day.
  - **Deviation from the request, deliberate (TASK-021):** the owner said not to worry about SMS length now that the messages come off his own SIM, and that is true of the *SMS* — but the body travels as a URL query parameter to a third-party relay with an unpublished request-line limit, which answers `200 ok` whether or not the parameter survived. All 15 at once is ~3,300 encoded characters with no way to observe truncation; three messages of five is ~1,100 each. The entries are numbered 1–15 continuously across the three so the reader can see none went missing. `build_vocabulary_sections()` is kept out of `CATEGORIES` so all three share one failure boundary: a missing notebook costs one `[unavailable: ...]` SMS, not three identical ones.

- [x] TASK-022: The brief arrived hours late because GitHub's scheduler is a queue. Move the clock off GitHub.
  - Context: the first fully unattended run, **2026-09-08**, was asked for at 03:00 UTC and started at **07:34 — 4h34m late**; the brief landed at 10:35 Istanbul. Nothing in this repo misbehaved: the job took 55 seconds, all 7 SMS were accepted, and the phone delivered them inside a minute. `docs/adr/0007` predicted a delay of this kind but sized it at ~20 minutes.
  - **The cheap fix was tried first and failed, which is what made the rest obvious.** The cron moved to `"47 2 * * *"` — off the top of the hour, GitHub's named high-load window, asking 13 minutes early. The next morning the run started at **10:34**, the same minute as the day before. Two samples, a 13-minute change in the request and a zero-minute change in the outcome: the cron expression was not choosing the time, so no edit to `daily-brief.yml` could have fixed it. Worth remembering as a method — one bad morning was ambiguous, and it was the *second* measurement that identified the cause rather than just confirming the symptom.
  - Fix: the `schedule:` block is deleted and `workflow_dispatch` is the only trigger. A MacroDroid time trigger on the owner's phone POSTs to `.../workflows/daily-brief.yml/dispatches` at 06:00 with body `{"ref":"main"}`. A dispatch is a request rather than a queued job, so it starts at once — the property that always made manual runs feel instant. Verified end to end on **2026-09-09**: the run appeared within seconds as "Manually run", a `dry_run` pass sent nothing, and the live pass delivered.
  - The cron was **deleted, not kept as a fallback**. It cannot tell that the phone already triggered a run, so its only effect would be a second brief every morning; a morning when the phone is off is a morning it could not have received the SMS anyway.
  - Costs accepted: a fine-grained PAT now lives on the phone (this repo only, `Actions: read and write`, so the worst case is an unwanted briefing) and it **expires silently** — when it does, the brief stops. More importantly the failure-notification argument in ADR 0007 is now weaker: GitHub only mails about runs that started, so a phone that never calls produces no run, no mail and no signal beyond a quiet morning.
  - Setup notes that cost time, now in README Part 3: MacroDroid's "Use authorization" is HTTP Basic and is the wrong field — the token goes in the **Header Params** tab as `Authorization: Bearer <token>`. Send `{"ref":"main"}` and omit `inputs` entirely; `dry_run` already defaults to false, and a nested JSON object typed on a phone keyboard is where a smart quote turns into a `400`. Local MacroDroid variables are `{lv=name}`, not `{v=name}` — the global syntax prints literally on screen.
  - Rejected: a third-party cron service (same token, held by a stranger instead of by the owner's own phone) and a launchd job on the Mac (asleep at 06:00, and it would bypass Actions rather than schedule it).

- [x] TASK-023: Record why the project exists, and audit what publishing the repository would expose.
  - The motivation was never written down anywhere: this was built for a year of military service with no internet, where SMS is the only channel that still arrives. That single constraint is what every earlier ADR was actually arguing from — per-category SMS (0004), the GSM-7 fold (0005), summarizing rather than linking — so README now states it once, up front, and the ADRs stop looking like preferences.
  - It also changes what "unattended" has to mean. Nobody will restart a failed run or replace an expired key, so the phone's PAT and the Anthropic credit are the two things worth setting to outlive the deployment; both fail silently and neither produces an email.
  - Public-repo audit, verified rather than assumed: `.gitignore` covers `.env` and `config/portfolio.json`; `git log --all` for both paths is **empty**, so no secret was ever committed; only `config/portfolio.example.json` is tracked. Secrets are masked and withheld from forks, and `workflow_dispatch` needs write access, so a stranger cannot trigger the brief. The phone number lives in the macro, not here.
  - Two things *do* become visible, and both are personal rather than confidential — `data/vocabulary.txt`, and the run logs. TASK-019's `stdout > /dev/null` is what keeps the briefing itself out of the log — the finding worth recording is the exception, `fetchers/portfolio.py` logging the **ticker** on a failed price lookup, so a bad morning names symbols held (never quantities or value).
  - ADR 0007's "making this repository public would leak the briefing" was stale — it predated TASK-019 discarding stdout — and is corrected. Going public also removes the minutes charge.
